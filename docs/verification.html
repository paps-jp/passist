🔐 検証に基づく安全性

PAssist のサーバが「GitHub で公開しているコードと同じ」ことを、数学（暗号学）で証明できる仕組みを採用しています。

0まず安心材料：そもそも見られない

サーバを信用するかどうかの前に、技術的に「サーバが映像を見られない」ことから整理します。

① 映像・音声・操作は P2P 直接通信

WebRTC によりホスト PC と相手のブラウザは 直接つながります。中央サーバは「最初の引き合わせ（シグナリング）」をするだけで、映像本体はサーバを通りません。

② 通信はすべて DTLS-SRTP で暗号化

映像・音声は AES-128-GCM、鍵交換は ECDHE (Curve25519)。鍵はホストと相手の端末でだけ生成され、サーバには一度も渡されません。

③ TURN 中継時も同じ

NAT 越えが難しい場合は TURN サーバが中継しますが、それは暗号化された塊（SRTP）を右から左に流すだけ。鍵を持たないので解読不可能です。

経路暗号化鍵を知るのは？
メディア（画面/音声）DTLS-SRTP / AES-128-GCMホストとビューアだけ
DataChannel（入力）SCTP over DTLS同上
TURN 中継時中継するのは暗号化済 SRTPTURN サーバは鍵を持たない

これだけでも「サーバが盗聴できる情報」はシグナリングの IP アドレスや接続時刻などのメタデータに限られます。映像の中身は数学的に守られています。

1WebRTC ＝ 数学的に解読不可能

WebRTC は SSL（TLS）の親戚である DTLS-SRTP を使います。

  • 鍵交換：ECDHE — 楕円曲線ディフィー・ヘルマン鍵共有（前方秘匿性）
  • 共通鍵暗号：AES-128-GCM — 認証付き暗号化（改ざんも検知）
  • 署名：ECDSA / Ed25519 — DTLS certificate fingerprint で対端末を認証

これらは NIST、IETF、TLS 1.3 で標準化されており、現在の数学的常識では破るには宇宙の年齢を超える計算時間がかかります。

2サーバが「公開コードと同じもの」であることを証明

WebRTC で守られているのは「中身（映像）」だけ。サーバ自体がコードを書き換えてメタデータを盗む可能性は理論的にゼロではありません。これを防ぐのが Reproducible Build + Cosign 署名です。

Reproducible Build（再現可能ビルド）

同じソースコードから誰がビルドしても、完全に同じバイト列の Docker image が生成される仕組みです。

PAssist の Dockerfile は SOURCE_DATE_EPOCH でファイルのタイムスタンプを git コミット時刻に固定し、npm ci で依存ツリーを package-lock.json 通り厳格に再現します。これにより、SHA-256 衝突困難性を根拠に「同じ digest なら同じバイト列」と言えます。

Cosign + Sigstore Rekor（鍵なし署名 + 公開ログ）

GitHub Actions が image をビルドした直後に、GitHub OIDC を使って秘密鍵なしで署名します。署名は公開の改ざん不可能な台帳 Sigstore Rekor（transparency log）に記録され、誰でも検証できます。

運営者が秘密鍵を持たないので、「鍵が漏れたら偽造できる」リスクがありません。

3信頼の連鎖

  1. Git コミット：ソース改ざんは SHA-256 ハッシュで検知（GitHub が保管）
  2. GitHub Actions が自動ビルド：ログは誰でも閲覧可能・改ざん不可能
  3. image を GHCR に公開：digest sha256:… が確定
  4. Cosign keyless 署名：「この image は github.com/paps-jp/passist の release ワークフローからビルドされた」を Sigstore に記録
  5. VPS で docker pull：pull した瞬間に digest が一致しなければエラー
  6. 誰でも検証可能：cosign verify + 自前で再ビルドして digest 一致を確認

4あなたが確認する手順

A. 公開 image の真正性（30秒）

cosign verify ghcr.io/paps-jp/passist-signaling@<digest> \
  --certificate-identity-regexp 'https://github.com/paps-jp/passist' \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com'

→ Sigstore Rekor の公開ログを参照して「この image は確かに paps-jp/passist の release ワークフローから生まれた」を検証します。

B. 自分でも同じ digest を再現（数分）

git clone https://github.com/paps-jp/passist
cd passist && git checkout v0.2.0
docker buildx build server \
  --build-arg SOURCE_DATE_EPOCH=$(git log -1 --format=%ct) \
  --provenance=mode=max --sbom=true -t local-rebuild
docker inspect local-rebuild --format='{{.Id}}'
# → 公開 digest と一致するはず

C. 運用中のサーバの自己申告

curl https://passist.paps.jp/api/build

サーバが動かしている commit / image digest / build時刻を返します。これ自体は嘘がつけるので、必ず A の cosign verify と突き合わせて判断します。

5ライセンス

PAssist のコードは、上記のような 安全性の検証を可能にするために公開しています。

✅ 自由にできること

  • 使うこと — 個人・法人を問わず、商用・非商用を問わず、PAssist を動かして自分の業務や支援活動、サービス提供に使うことは自由です。
  • 自分のサーバで PAssist を立てて、社内・組織内・自社サービスとして運用すること。
  • コードを読んで監査・検証すること、安全性を確認するために自分でビルドして再現性を確かめること。

⚠ ご遠慮いただいていること

  • コードや改変版を第三者に再頒布・販売すること。
  • PAssist の派生物（フォーク・改造版）を独自の製品として商用提供すること。
  • コードの一部・全部を別ソフトウェアに組み込んで販売すること。

これは「サービスとしての利用は自由」「コードそのものの商業化は控えていただく」という方針です。技術的な検証のためにコードを公開しつつ、開発の継続性と品質を保つためのものです。
